> **本报告性质**:固化 DesignOS 知识库 / 方法论 / 模板 / 案例 / failure modes 的放置规则,防止 S2-H3 / S2-H4 继续扩展时制造双源或混乱。

## 1. 当前结构盘点

DesignOS 的"知识"分布在三个物理层,职责不同,不可混淆:

### 1.1 共享知识层 — `knowledge/`

```
knowledge/
├── manifest.yaml          # ★ active source-of-truth(51 资产,按 stable id)
├── README.md              # 架构守则(本批已扩充)
├── INDEX-BY-TYPE.md       # 按 type 汇总的索引(本批新增,非真源)
├── design/  ux/  product/  frontend/  research/   # domain-first 物理目录
└── design-work-paradigm/  # methodology reference library(40 方法,非 skill 接入真源)
```

- **物理切分按 domain**(design/ux/product/frontend/research)。
- **资产类型真源是 manifest 的 `type` 字段**,不是物理目录(同一 `design/quality/` 目录混放 rubric + failure_modes + checklist)。
- 当前 51 资产,8 种 type:methodology / principles / standard / rubric / failure_modes / checklist / report / template。

### 1.2 Skill 私有层 — `skills/<skill>/`

```
skills/<skill>/
├── SKILL.md                  # 能力声明 / 边界
├── constitution.md           # 硬约束(failure modes 的检测基础)
├── pipeline.yaml             # 流程(stage 顺序 / gate)
├── prompts/ prompts-v2/      # 执行层
├── reference/m0x-*.md        # 方法论适配层(如何在本 skill 应用共享知识)
├── templates/                # 输出模板(含 S2-H2 golden template)
├── knowledge-manifest.yaml   # 声明本 skill 复用哪些共享 asset id
└── eval/golden/ eval/failure/  # 案例(golden / failure case)
```

### 1.3 审计与治理层 — `docs/audits/` + `.claude/skills/`

- `docs/audits/S1-0* / S2-H*`:盘点、决策、rubric、OKR、golden、failure 等审计文档。
- `.claude/skills/designos-*`:governor / closeout / knowledge-architect / skill-factory 治理 skill。

## 2. 为什么不大搬家

S1-0B 已裁定真源,且各 skill 的 `knowledge-manifest.yaml` 已按 stable id 锚定(S2-1 commit `3feb01f` 已修复 24 个 id 的实现锚点)。此时大规模移动文件的代价远大于收益:

1. **stable id 是引用契约,不是路径**。资产按 `<domain>.<slug>` 引用,文件移动不改 id——所以"分类不完美"不影响引用正确性。搬家只动物理路径,不解决任何真实问题。
2. **搬家会使 `manifest.yaml` 的 51 个 `source_of_truth` 路径全部失效**,需同步重写 + 重测,引入回归风险。
3. **S2-1 刚锚定的 reference 锚点会被打散**,可能再次制造"声明 vs 实现"断裂。
4. **domain-first 已经是合理结构**(见 README §为什么不是一个大目录):每个 domain 有独立专家心智,skill 通常只消费一两个 domain。

**结论**:用"规则 + 索引"固化分类,而非"搬家"。type 检索需求由 `INDEX-BY-TYPE.md` 满足。

## 3. 放置规则(通用资产 vs 专用资产)

### 3.1 判定口诀(沿用 README)

> 一条知识进共享层,当且仅当:**删掉正文里所有 skill 名 / 产品名后,它依然完整成立、且对另一个 skill 仍有用。** 否则它是 skill 私有 reference。

### 3.2 四类内容的归属表

| 内容类型 | 放哪里 | 真源标记 | 反例(不要这样) |
|---|---|---|---|
| 通用方法论 / 原则 / 标准 / rubric / failure_modes | `knowledge/<domain>/`,登记进 `manifest.yaml` | manifest stable id | ❌ 复制进某 skill 的 reference |
| skill 如何应用通用知识 | `skills/<skill>/reference/m0x-*.md` | skill 私有 | ❌ 提进 knowledge 通用正文 |
| skill 输出模板 | `skills/<skill>/templates/` | skill 私有 | ❌ 当作共享 asset 登记 manifest |
| 具体 golden / failure 案例 | `skills/<skill>/eval/golden/`、`eval/failure/` | skill 私有 | ❌ 写进 knowledge 通用正文 |
| 方法论参考(40 范式) | `knowledge/design-work-paradigm/` | reference library(**非** skill 接入真源) | ❌ 让 skill 按编号 01-19 引用 |

### 3.3 两套 manifest 的关系(S1-0B 裁定的固化)

| | `knowledge/manifest.yaml` | `knowledge/design-work-paradigm/manifest.yaml` |
|---|---|---|
| 角色 | **active source-of-truth** | methodology reference library 索引 |
| skill 接入 | ✅ 各 skill 的 knowledge-manifest 按 stable id 引用 | ❌ 无 skill 按方法编号引用 |
| 命名 | `<domain>.<slug>`(如 `ux.severity-rubric`) | 编号(00-39) |
| 校验 | 结构测试 + 本报告 §6 路径校验 | `scripts/validate-paradigm-manifest.py` |

## 4. S2-H3 Failure Modes 放置决策

S2-H3 要为 5 skill 建 failure mode library。**放置规则如下,禁止制造第二套 failure 真源**:

### 4.1 已有 failure 资产(不可重复,只可引用)

| 资产 | 路径 | 角色 |
|---|---|---|
| 通用失败模式(设计推理) | `knowledge/design-work-paradigm/18-failure-modes.md` | 方法论参考 |
| IP 设计失败模式 | `knowledge/design/quality/common-failure-modes.md`(`design.quality.common-failure-modes`) | 共享 asset |
| 品牌创意失败模式 | `knowledge/design/quality/brand-creative-failure-modes.md`(`design.quality.brand-creative-failure-modes`) | 共享 asset |
| UX 失败模式 | `knowledge/ux/ux-failure-modes.md`(`ux.ux-failure-modes`) | 共享 asset |
| 各 skill 具体 failure case | `skills/<skill>/eval/failure/*` | skill 私有案例 |

### 4.2 S2-H3 放置规则

1. **skill-specific failure mode 结构化清单** → 放 `skills/<skill>/eval/failure/failure-modes.md`(skill 私有,与现有 case 同目录)。
2. **失败模式正文如已存在于上述共享 asset** → S2-H3 **只引用其 id / 章节,不复制正文**。例如 ip-design 的 failure-modes.md 引用 `design.quality.common-failure-modes` 而非重写。
3. **统一 failure library 总表** → 放 `docs/audits/S2-H3-FAILURE-MODE-LIBRARY.md`,作为 S2-H1/H2 的配套审计层,**映射**(不复制)到各 skill 的 failure-modes.md + 现有共享 asset。
4. **不新增共享 knowledge asset**(除非发现某 skill 完全无 failure 资产且无法复用——届时须先在本 guardrails 报告登记理由)。
5. failure mode 的 `delivery_decision`(block/degrade/warn/gap)语义,对齐 `design-work-paradigm/18` 的 `blocked / fallback / warning` 三态,不发明新枚举。

## 5. S2-H4 Self Review Gate 引用决策

S2-H4 要建 self review gate。**它是"引用层",不产生新标准**:

1. **评分标准** → 引用 S2-H1 §5 rubric 表 + 各 skill 现有 rubric asset(如 `design.quality.ip-design-quality-rubric`)。
2. **通过/阻塞判据** → 引用 S2-H1.1 的 KR 编号 + 一票否决项(22 项):KR 全通过 = gate 通过;任一一票否决命中 = gate 阻塞。
3. **failure 检测** → 引用 S2-H3 的 failure-modes.md 的 `detection_signal` + `delivery_decision`。
4. **输出模板对账** → 引用 S2-H2 各 skill golden template 的"自评表"。
5. **术语纪律** → self review gate 是文档/prompt 层的自检规范,**不得**称为 kernel `quality_gates:`(那是 runtime 真 blocking,仅 prd2proto 接入);uxeval/ai-analytics/ip-design 的 pipeline `gate:` 是 checkpoint 暂停门,语义不同(S1-0C 已固化此区分)。
