# 竞品调研报告：Agent 与 Skills 封装、记忆与自主进化生态

> 编写日期：2026-05-15
> 作者：Claude (基于训练知识 + 公开资料)
> 用途：为「Agent-design 项目封装为可共享、自主进化、带记忆的 Agent / Skills」提供决策依据

---

## 摘要

当前 Agent 生态正从「框架百花齐放」向「协议层收敛」演进。三条最重要的标准化主线已经稳定：**Anthropic MCP**（工具/上下文标准）、**Anthropic Agent Skills / Claude Code Skills**（能力封装标准）、**Google A2A**（Agent 互操作标准）。封装形态上，Markdown + Frontmatter 已经成为事实上的「Skill 单元」格式（Claude Skills、Cursor Rules、Continue Rules 全部采用），这与你已有的 11 份 Markdown 知识库天然契合。记忆层 mem0 / Letta / Zep 三家分占主流；自主进化层学术界 Reflexion / Voyager / DSPy 提供原型，工业界 LangSmith / Braintrust / Phoenix 提供 Eval 基础设施。

**对你项目的最关键决策点**：
1. **封装形态**：采用 Anthropic Agent Skills 的 `SKILL.md` 格式作为单元，每个领域 Agent 是一个 Skill 包，仓库结构遵循「Kernel + Domain Pack」分层
2. **分发渠道**：GitHub monorepo（短期） + 自建 Skill Registry（中期） + 接入集团 MCP Server（长期）
3. **记忆架构**：分三级（会话/项目/组织），用 mem0 或自研轻量方案，知识库继续以 Markdown 为主
4. **自主进化**：完整复刻你方案文档中的飞轮，工具栈选 Promptfoo（评估）+ DSPy（Prompt 优化）+ GitHub Actions（回归）
5. **核心警惕**：不要盲目追求多 Agent 编排框架，Skills + 简单 Pipeline 比复杂图编排更易维护、更易共享

## 一、Skills / Agent 封装与分发标准

### 1.1 Anthropic Agent Skills（最核心，强烈推荐）

**现状**：Anthropic 在 2025 年推出 Agent Skills 概念，是 Claude.ai、Claude Code、Claude Agent SDK 三端共用的能力封装标准。每个 Skill 是一个目录，含一份 `SKILL.md`（YAML frontmatter + Markdown 正文）+ 可选的资源文件、脚本、模板。

**目录结构**：
```
my-skill/
├── SKILL.md              # 必需：含 name/description 等 frontmatter
├── reference/            # 可选：参考文档、知识库
├── scripts/              # 可选：辅助脚本
├── templates/            # 可选：模板文件
└── examples/             # 可选：示例
```

**SKILL.md 格式**：
```markdown
---
name: my-skill
description: One-line summary used for skill discovery
---

# Skill instructions
模型在被触发时会读取这段 Markdown 作为系统指令...
```

**关键设计**：
- **模型自主调用**：Skill 由模型根据 description 决定何时调用（不像 slash command 由用户显式触发）
- **渐进式披露**：SKILL.md 主体精炼（几百字），详细方法论放在 reference/ 子目录，按需加载
- **零依赖**：纯 Markdown + 文件系统，不绑定任何 SDK
- **跨产品**：同一个 Skill 包可在 Claude Desktop、Claude Code、Agent SDK 之间迁移

**对我们的可借鉴点**：
- 你现有的 6 个 Agent 文档（每个 6-9 子 Agent + 10-13 份 Markdown 知识库）几乎可以无损映射为 6 个 Skill 包
- Skills 的「渐进式披露」与你 prd2proto 文档中提炼的「渐进式披露经验」完全一致
- GitHub 分发天然支持（git clone 到 `~/.claude/skills/` 即可使用）

**不适用点**：
- Skill 默认只在 Claude 生态可用；如需跨模型/跨平台，需额外适配层
- 单 Skill 适合「单一能力」，复杂多 Agent 编排（你 6 阶段流水线）需要在 Skill 内部用 Pipeline 自管理

**链接**：
- 官方文档：`docs.claude.com/en/docs/agents-and-tools/agent-skills`
- Claude Code Skills 目录：`~/.claude/skills/` 或项目内 `.claude/skills/`

---

### 1.2 Claude Code Slash Commands（轻量补充）

**现状**：Claude Code 同时支持 Skills（模型调用）和 Slash Commands（用户调用）两种封装形式，Commands 位于 `.claude/commands/` 或 `~/.claude/commands/`，每个 `.md` 文件成为一个 `/命令名`。

**格式**：
```markdown
---
description: Short description
argument-hint: <expected args>
allowed-tools: Bash(git diff:*), Read, Edit
model: claude-sonnet-4-5
---
# Command prompt body
Use $ARGUMENTS for user input. Use !`bash cmd` for shell. Use @path for file include.
```

**借鉴**：每个 Agent 子流程（如「生成评估报告」「输出物料清单」）可同时提供一个 slash command 入口给设计师手动触发，作为 Skill 的补充。

---

### 1.3 OpenAI Custom GPTs / Assistants API

**现状**（截至 2025-2026）：
- **Custom GPTs**：no-code 方式创建定制 ChatGPT，在 GPT Store 分发；适合 C 端
- **Assistants API**：开发者 API，2025 年 3 月被 **Responses API** 替代，2026 年内全面下线
- **Agent 方向**：OpenAI 在 2025 年发布 Operator（浏览器 Agent）、ChatGPT Agent 模式

**关键设计**：
- Custom GPT 通过 manifest（说明 + 知识文件 + Actions）封装
- Assistants 通过 thread + tool 抽象，记忆在 OpenAI 服务端

**对我们的不适用点**：
- 闭源、绑定 OpenAI、企业内自建场景需要供应商解耦
- GPT Store 是消费端，集团内分享更适合自建 registry
- Assistants API 即将下线，不应作为基础

**借鉴点**：Custom GPT 的「指令 + 知识文件 + Actions」三件套结构与 Skill 思路一致，可作为对照

---

### 1.4 Cursor Rules / Continue Rules / Aider Conventions

**现状**：编辑器内 AI 助手（Cursor、Continue.dev、Aider）都采用类似的「Markdown 配置 + 项目根目录约定」方案：
- Cursor：`.cursorrules` 或 `.cursor/rules/*.mdc`（含 frontmatter）
- Continue：`.continuerules`、`config.yaml`
- Aider：`.aider.conf.yml` + 约定文件

**关键设计**：纯文本配置 + Git 版本控制 + 项目级/全局级双层

**借鉴**：你的 6 个 Agent 包内可分别带 `.cursorrules`，让用户在 Cursor 中也能用同一套规范

---

### 1.5 LangChain Hub

**现状**：LangChain 维护的 Prompt / Chain 共享平台 `smith.langchain.com/hub`，社区可发布、检索、版本化 Prompt 模板。

**借鉴**：「prompt 带版本号」「pull/push 模型」的工程实践可复用，但你的 Agent 远比单个 prompt 复杂，Hub 不能直接装下整个 Skill 包。

---

### 1.6 MCP (Model Context Protocol) — 工具分发标准

**现状**：Anthropic 2024 年 11 月发布的开放协议，2025 年内被 OpenAI、Google、IDE 厂商（Cursor、Continue、Zed）广泛采纳，已经成为「LLM 与外部工具/数据源的事实标准」。

**架构**：客户端-服务端架构。MCP Server 暴露 tools / resources / prompts，MCP Client（Claude Desktop、Cursor 等）连接消费。

**生态**：
- 官方 Server：filesystem、git、GitHub、Slack、Postgres 等
- 第三方 Registry：**Smithery** (`smithery.ai`)、**mcp.so**、**PulseMCP**
- 安装方式：通过 registry CLI 一键添加，或在客户端配置文件中声明

**对我们的关键启示**：
- 你的 Agent 中那些「读 PRD / 抓截图 / 浏览器采集 / 生成 Excel 报告」等工具能力，应该独立封装为 MCP Server
- Skill 调用 MCP Server，而非把工具逻辑写死在 Agent 里
- 将来集团内可能要建私有 MCP Registry（比如基于 mcp.so 的开源代码自建）

**链接**：
- `modelcontextprotocol.io`
- `github.com/modelcontextprotocol`
- `smithery.ai`

---

### 1.7 HuggingFace Spaces / Replicate

**现状**：偏重模型推理的 demo 分发，非 Agent 封装格式
**借鉴**：仅作为「带 GPU 的 Agent 运行时」的备选托管平台，不影响封装格式选型

## 二、Agent 记忆系统的工业实践

### 2.1 记忆分层的标准模型

学术与工业界已形成共识的三层模型：

| 层级 | 学术叫法 | 内容 | 生命周期 | 典型实现 |
|---|---|---|---|---|
| **工作记忆** | Short-term / Working | 当前对话的 token | 对话内 | 模型上下文窗口 |
| **情景记忆** | Episodic | 历史交互、过往项目 | 跨会话/跨项目 | mem0、Zep、向量库 |
| **语义记忆** | Semantic | 知识、事实、规则 | 长期稳定 | 知识图谱、知识库 |
| **程序性记忆** | Procedural | 技能、流程 | 长期稳定 | Skills 包本身 |

**对我们的映射**：
- 工作记忆：单次评估/原型生成的中间产物
- 情景记忆：「上次我们给某产品做评估时的判断」「设计师对某类问题的偏好」
- 语义记忆：你的 Markdown 知识库（启发式原则、武侠原型、PEST 模型等）
- 程序性记忆：Skill 本身的 Pipeline 定义

---

### 2.2 mem0（最主流，推荐）

**现状**：开源记忆层，GitHub stars 高（>20k 量级），多语言 SDK（Python、Node.js）。2026 年初的 benchmark 显示其在记忆基础任务上比 OpenAI 内置记忆高 26% 准确率。

**架构**：
- 自动记忆抽取：从对话中识别需要记忆的事实
- 多 backend：向量库 (Qdrant/Chroma/pgvector) + 图数据库 (Neo4j) 可选
- 三种记忆类型：User / Session / Agent
- API 极简：`m.add()` / `m.search()` / `m.update()`

**借鉴**：作为记忆层首选，特别是「设计师偏好」「项目历史」这类可以让 mem0 自动管理的内容。

**链接**：`github.com/mem0ai/mem0`、`docs.mem0.ai`

---

### 2.3 Letta（前 MemGPT）

**现状**：从 MemGPT 论文演变而来的开源 Agent 平台，强调「Agent 自管理记忆 + 长期运行」。2025-2026 年发布 Letta v1，借鉴 ReAct + MemGPT + Claude Code 重构 Agent 循环。

**关键设计**：
- 把记忆做成 Agent 的「内存管理工具」，模型自己决定何时写/读
- 支持 stateful agent，可长期运行
- 自带可视化 Agent Studio

**借鉴 vs 不适用**：
- 适合：需要长期运行的客服、研究 Agent
- 不适合：你的设计 Agent 是任务型（项目周期 1-2 周），不需要 24/7 stateful
- 借鉴：「记忆作为工具」的思路可以借用到 Skills 内部

---

### 2.4 Zep

**现状**：商业化记忆层，开源版本叫 Zep Community Edition。强调「时间感知 + 知识图谱」。

**关键设计**：自动构建用户/实体的时间线知识图谱（叫 Graphiti），适合「事实随时间演变」场景

**借鉴**：你的「集团内品牌资产」「历史 IP 设定」可能需要时间维度的演变追踪，Zep 的 Graphiti 思路可以参考

---

### 2.5 LangChain Memory / LangGraph Checkpointer

**现状**：LangChain 的 Memory 模块主要是会话级 buffer；LangGraph 的 Checkpointer 是「可恢复的图执行状态」（持久化中间产物）

**借鉴**：Checkpointer 思路适合你的 6 阶段 Pipeline——每个阶段产物入库，支持中途暂停、回滚、重跑

---

### 2.6 LlamaIndex 记忆抽象

**现状**：偏重 RAG 场景的「文档 + 索引」，2025 年增加了 Agent Memory 模块

**借鉴**：你的 Markdown 知识库本质就是 LlamaIndex 的 Document，可用其做检索增强（如果需要）

---

### 2.7 ChatGPT / Claude 内置 Memory

**现状**：
- ChatGPT Memory：2024 年公测，跨会话记忆用户偏好，模型自决定记什么
- Claude Memory：2025 年随 Claude.ai 推出，类似机制
- Claude Code Memory：基于 `CLAUDE.md` + 持久化 memory 目录（即你当前看到的我用的这套）

**借鉴**：Claude Code 的 Memory 模型（Markdown 文件 + 索引 MEMORY.md + 类型化分类）非常适合你的场景，可直接复用其设计

## 三、Agent 自主进化的工程化

### 3.1 Eval-driven Development（最重要的工程实践）

**核心理念**：不靠感觉改 Prompt，每次改动跑评估集，看分数变化决定是否合入。

**主流工具栈**：
| 工具 | 定位 | 特点 |
|---|---|---|
| **LangSmith Evaluation** | LangChain 生态 | 完整 trace + dataset + experiment 对比 |
| **Braintrust** | 商业评估平台 | 强调实验管理、CI 集成 |
| **Arize Phoenix** | 开源 | 自托管友好，OpenTelemetry 兼容 |
| **Promptfoo** | 开源轻量 | YAML 配置、CLI 跑、CI 集成 |
| **OpenAI Evals** | OpenAI 官方 | 框架化但生态主要在 OpenAI |
| **Ragas** | RAG 专项 | faithfulness / context precision 等 RAG 指标 |
| **DeepEval** | 开源单元测试风格 | pytest-like，做 LLM 测试 |

**对我们的推荐**：
- **轻量起步用 Promptfoo**（YAML + CLI，与 GitHub Actions 集成最简单）
- **规模化后接 LangSmith 或 Phoenix**（trace 完整、UI 好）
- 评估宪法（你方案文档中提到的）应该实现成评估器规则文件，跟 Skill 一起进版本控制

**链接**：`langsmith.langchain.com`、`promptfoo.dev`、`docs.arize.com/phoenix`、`docs.ragas.io`

---

### 3.2 学术原型：Self-Refine、Reflexion、Voyager

**Self-Refine**（2023）：先生成 → 自我批评 → 修订，单 Agent 反思
**Reflexion**（2023）：失败经验写入「episodic memory」，下次任务前读取
**Voyager**（2023）：Minecraft 中的开放式 Agent，把学到的技能写入「skill library」，越玩越会玩
**Generative Agents**（Stanford 小镇，2023）：每个 Agent 都有 reflection + memory stream

**对我们的关键启示**：
- **Voyager 模式最值得借鉴**：让 Agent 把「成功的判断模式」沉淀回 Skills 库，但写回必须经过专家审批（这正是你方案文档的「人类放行」原则）
- **Reflexion 的 episodic memory**：每次评估失败时，把「为什么失败」写入对应 Skill 的 failure case 库，下次同类任务前读取
- **不要盲目复制学术界的「全自主进化」**：你的方案文档已经正确指出——人类放行才是企业场景的现实路径

**新动向（2025-2026）**：
- **NousResearch/hermes-agent-self-evolution**（GitHub）：用 DSPy + GEPA 做 skill / prompt / code 的进化优化
- **学术界讨论 Self-evolving Agents 的「emergent risks」**：自主进化系统出现的对齐风险、目标漂移
- **2025 多篇论文聚焦「Self-evolving Multi-Agent Evaluation」**：Agent 互相评估对方的进化方向

---

### 3.3 Prompt / Program 优化工具

**DSPy**（Stanford，开源）：
- 把 Prompt 当作「可优化的程序」
- 给定 metric + dataset，自动搜索更优 Prompt 或 few-shot
- 适合「我有评估集，想自动找最佳 Prompt」场景

**TextGrad**：把 LLM 输出当作「可微的 token」做梯度优化

**OpenAI Prompt Optimizer**：闭源，OpenAI 平台内功能

**PromptLayer**：Prompt 版本管理 + A/B 测试 SaaS

**对我们的推荐**：你方案文档「阶段 3：半自动优化」对应的工具就是 DSPy。建议 UXEval 跑通评估集后用 DSPy 自动优化 Prompt 版本。

**链接**：`dspy.ai`、`github.com/stanfordnlp/dspy`

---

### 3.4 Constitutional AI / RLAIF

**Anthropic Constitutional AI**：用一组宪法原则约束模型，让 AI 评判 AI 的输出
**RLAIF**：用 AI 反馈替代人类反馈做 RL 训练

**对我们的关键启示**：你方案文档中提到的「评估宪法」就是 Constitutional AI 思路在垂直领域的应用。每个 Skill 应该附带一份「领域宪法」（如 UXEval 的 7 条评估宪法），同时是评估器和约束器。

---

### 3.5 Human-in-the-loop 工具

**LangGraph 审批节点**：图执行可在指定节点暂停等人工审批
**Humanloop**：商业化 HITL 平台
**Argilla**：开源标注平台，适合做「专家标注样本」

**借鉴**：你 Pipeline 的每个 Checkpoint（C1-C5）都是 HITL 节点，LangGraph 的 interrupt 机制可作为底层实现参考

## 四、多 Agent 编排与协议

### 4.1 LangGraph（开源，最严谨）

**定位**：基于状态图（StateGraph）的 Agent 编排，LangChain 出品，2024-2025 年成为多 Agent 编排事实标准之一，2026 年发布 v1。

**核心抽象**：
- Node：执行单元（LLM 调用、工具调用、人工审批）
- Edge：状态转移（条件、并行、循环）
- State：贯穿整图的可变状态
- Checkpointer：状态持久化

**优点**：可视化清晰、调试友好、HITL 内置
**缺点**：学习曲线陡，过度工程化风险

**对我们的判断**：你的 6 阶段 Pipeline 完全可以用 LangGraph 实现，但**不必要**。Skills 内部用简单的「顺序 Pipeline + Checkpoint」就够，复杂图编排留给真正需要的场景。

**链接**：`langchain-ai.github.io/langgraph`

---

### 4.2 CrewAI（开源，团队隐喻）

**定位**：用「团队 + 角色 + 任务」隐喻做多 Agent 编排，更贴近业务人员心智模型

**核心抽象**：
- Agent：有 role / goal / backstory 的角色
- Task：分配给 Agent 的任务
- Crew：Agent 的集合 + 执行流程
- Tools：Agent 可用的工具
- Flows（2025 新增）：更精细的流程控制

**优点**：上手快、隐喻直观，PyPI `crewai` + `crewai-tools`
**缺点**：抽象不如 LangGraph 严谨，复杂场景容易失控

**对我们的判断**：CrewAI 的「角色 + 任务」隐喻**和你 Agent 文档的叙事高度契合**（每个子 Agent 都有明确角色和职责），但实际生产建议优先 Skills + 简单 Pipeline，CrewAI 作为快速 prototype 工具备选。

**链接**：`docs.crewai.com`、`github.com/crewAIInc/crewAI`

---

### 4.3 AutoGen（微软，开源）

**定位**：微软研究院的多 Agent 对话框架，2024 年发布 v0.4 大重构

**核心抽象**：actor-based、消息驱动、对话即编排
**优点**：理论扎实、灵活
**缺点**：抽象层次较低，工程实践需要自己组装

**对我们的判断**：暂不推荐作为主框架，但其「Agent 互相对话推进任务」的范式可作为后续探索。

---

### 4.4 OpenAI Swarm / Magentic-One

**Swarm**：OpenAI 2024 年发布的极简多 Agent 编排教学库（已转为「学习参考」状态）
**Magentic-One**：微软 2024 年发布的通用多 Agent 系统

**对我们**：仅作为参考，不直接采用

---

### 4.5 Agent 互操作协议

**Anthropic MCP**：工具/上下文层（已是事实标准）
**Google A2A (Agent2Agent)**：2025 年 4 月发布，Agent 间互操作协议
- 定义 Agent Card（自我描述）
- HTTP/JSON-RPC + SSE 流式
- 任务委派、状态查询
**IBM ACP (Agent Communication Protocol)**：BeeAI 项目下的标准
- RESTful、多模态消息
- 2025 年 BeeAI 加入 Linux Foundation，与 A2A 讨论合并

**对我们的关键启示**：
- 短期：MCP 必用（封装工具）
- 中期：Agent 之间用简单 HTTP/JSON 通信即可，A2A/ACP 标准化后再迁移
- 长期：观察 A2A 与 ACP 的合并进展，集团若要建多团队 Agent 协作必须采纳

---

### 4.6 Workflow as Code / DAG / 自由对话路由

**三种范式对比**：

| 范式 | 代表 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **顺序 Pipeline** | Skills 内部 | 简单、可读 | 不能动态分支 | 你的 6 阶段流水线 |
| **DAG / StateGraph** | LangGraph | 强表达力、可视化 | 复杂 | 真正需要分支的场景 |
| **自由对话路由** | AutoGen、CrewAI | 灵活 | 不可预测 | 探索式任务 |

**对我们的明确建议**：**优先顺序 Pipeline**。你的 6 个 Agent 全部是稳定的「理解→建模→执行→检查→沉淀」骨架，没有真正需要 DAG 的分支。把 Pipeline 写在 SKILL.md 内部就够，不引入额外编排框架。

## 六、共享 / 治理 / 版本管理

### 6.1 GitHub 上 Agent 仓库的组织形式

| 形式 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **Monorepo** | LangChain、CrewAI | 统一版本、共享代码、原子提交 | 仓库大、构建慢 |
| **多仓 + Org** | Anthropic SDKs、MCP servers | 解耦清晰 | 跨仓更新难协调 |
| **Registry + 仓库** | Smithery、mcp.so | 发现性好 | 需建注册中心 |

**对我们的建议**：
- **第一阶段（现在 - 3 个月）**：单 monorepo `agent-design/`，6 个 Skill 包作为子目录
- **第二阶段（3-6 个月）**：拆为 `agent-design-kernel`（内核）+ `agent-design-skills/*`（每个 Skill 独立仓库）
- **第三阶段（6+ 个月）**：建集团内 Skill Registry，提供检索 / 评分 / 一键安装

---

### 6.2 版本管理与发布流程

**Semantic Versioning**（标准做法）：
- MAJOR：不兼容的 API 变更
- MINOR：向后兼容的新功能
- PATCH：bug 修复

**Skill 特有的版本维度**：
- Prompt 版本（独立于代码版本）
- 知识库版本（Markdown 文档变更）
- 评估宪法版本

**发布流程建议**：
1. PR 提交 → 自动跑 eval 回归（GitHub Actions）
2. 评估集得分不退步 + 至少 1 名设计专家 review
3. 合入 main → 打 tag → 生成 CHANGELOG
4. 灰度：先发 beta 给种子用户，1 周后稳定再 promote 到 stable

---

### 6.3 安全 / 审计 / 数据隐私

**企业内分享的关键关注点**：

1. **敏感数据隔离**：
   - PRD、设计稿可能含商业机密
   - Skill 内不能包含真实项目数据，只放脱敏样本
   - 评估集如含真实数据，仓库需私有 + 访问控制

2. **Prompt Injection 防护**：
   - 用户上传的 PRD 可能含指令注入
   - 在 Agent 内部加「指令隔离层」（XML 标签或显式分隔）

3. **凭证管理**：
   - `.env.local`、API key 用 secret manager（如 doppler、1Password）
   - 仓库内只放 `.env.example`

4. **审计日志**：
   - 每次 Skill 调用记录：谁、何时、用了哪个版本、输入输出摘要
   - 集团合规要求可能需要保留 6 个月以上

5. **License 与合规**：
   - 内部分享建议用 Apache 2.0 / MIT
   - 如未来开源需 review 是否引入 GPL 依赖

---

### 6.4 Skill Marketplace 的发现性机制

参考 Smithery / mcp.so / GPT Store 的做法：
- **元数据标准**：name、description、tags、version、author、依赖
- **评分系统**：使用次数、用户评分、专家认证
- **依赖管理**：Skill 依赖其他 Skill 时声明
- **签名机制**：作者签名 + 集团审核标记

**对我们的建议**：第一版不做 marketplace，先用 GitHub topic + README 中的 badge；用户量上来后再考虑自建 registry。

## 八、对本项目的具体启示

### 8.1 封装形态选型建议

**主选方案：Anthropic Agent Skills + MCP Server 二合一**

```
agent-design/
├── kernel/                          # 通用内核（共享给所有 Skill）
│   ├── pipeline-engine/
│   ├── checkpoint-system/
│   ├── evidence-system/
│   └── output-templates/
├── skills/                          # 6 个领域 Skill 包
│   ├── uxeval/
│   │   ├── SKILL.md                # Anthropic Skill 标准格式
│   │   ├── reference/              # 知识库（11 份 Markdown）
│   │   ├── templates/              # 模板（任务清单、问题表）
│   │   ├── examples/               # 示例（黄金样本）
│   │   ├── eval/                   # 评估集（黄金 + 失败）
│   │   ├── prompts/                # 带版本号的 Prompt
│   │   └── constitution.md         # 评估宪法
│   ├── prd2proto/
│   ├── design-system/
│   ├── ip-design/
│   ├── brandcreative/
│   └── ai-analytics/
├── mcp-servers/                     # 工具层
│   ├── pdf-parser/                 # 解析 PRD
│   ├── browser-capture/            # 浏览器截图
│   ├── excel-builder/              # 输出 Excel
│   └── design-token/               # MasterGo Token 提取
├── docs/                           # 项目文档
├── .github/workflows/              # CI（含 eval 回归）

```

**为什么这样选**：
1. Skills 标准格式天然兼容 Claude 生态（你已用 Trae IDE，迁移到 Claude Code 几乎零成本）
2. 工具能力封装为 MCP Server，可被任何 MCP 客户端复用（不绑定 Claude）
3. Markdown 知识库直接放 reference/，与你现有 11 份文档一致
4. 评估宪法、Prompt、评估集明确分离，符合自主进化飞轮

---

### 8.2 记忆架构选型建议

**三级记忆 + 不同存储**：

| 层级 | 内容 | 实现 | 谁能写 |
|---|---|---|---|
| **会话记忆** | 本次评估的上下文 | 进程内变量 + Checkpointer 持久化 | Agent 自动 |
| **项目记忆** | 该项目的旅程、问题、决策 | 项目目录下 Markdown + JSON | Agent + 设计师 |
| **组织记忆** | 黄金样本、失败案例、专家偏好 | mem0（向量库）+ Markdown 知识库 | **仅设计师审批后** |

**关键纪律**（来自你方案文档的「人类放行」原则）：
- Agent 可以「提议」更新组织记忆（写到 staging）
- 必须设计师在 GitHub PR 中 review 通过才合入
- 自动评估器只能筛选候选，不能自动合入

---

### 8.3 自主进化机制选型建议

**完整工具链**：

| 阶段 | 工具 | 落地形式 |
|---|---|---|
| **Trace** | LangSmith / Phoenix（自托管） | OpenTelemetry 兼容，所有 Agent 调用全 trace |
| **评估集** | YAML + Markdown | 黄金 + 失败两类，进版本控制 |
| **自动评估** | Promptfoo + 自定义 LLM judge | GitHub Action 每次 PR 跑 |
| **Prompt 优化** | DSPy（阶段 3） | 离线跑，输出候选 Prompt，专家选 |
| **版本管理** | Git tag + CHANGELOG | Prompt 和评估集都打 tag |
| **审批** | GitHub PR review | 至少 1 名设计专家 + CI 通过 |
| **灰度** | Skill 多版本共存 | beta 标签 → 1 周观察 → stable |

**关键路径**（与你方案文档完全对齐，只是把工具填实了）：

```
专家手工评估 (阶段 1)
    ↓
建立评估集 → Promptfoo 自动评估 (阶段 2)
    ↓
DSPy Prompt 优化 → 专家审批 (阶段 3)
```

---

### 8.4 多 Agent 编排选型建议

**明确建议：不引入复杂编排框架**

理由：
1. 你的 6 个 Agent 都是稳定的顺序 Pipeline，没有动态分支需求
2. Skills 内部用简单状态机（YAML 配置 + 几行 Python）即可表达
3. 引入 LangGraph/CrewAI 会让 Skill 包变重，不利分享
4. Anthropic Skills 设计哲学就是「让模型 + Markdown 自管理」，复杂编排是反模式

**如果未来真的需要**：把 LangGraph 作为「内核」的 optional 依赖，让某个 Skill 在需要时引入；但默认不依赖。

---

### 8.5 共享与治理选型建议

**三阶段路线图**：

**阶段 1（0-3 月）：单 Monorepo + GitHub**
- 一个仓库容纳全部 6 个 Skill + Kernel + MCP Servers
- README 写清楚装法、用法、贡献指南
- 集团内同事 git clone 即用
- 用 GitHub Issues 收集反馈

**阶段 2（3-6 月）：拆仓 + 自动化**
- Kernel 独立仓库（稳定后版本化）
- 每个 Skill 独立仓库（独立 release 节奏）
- GitHub Actions 跑 eval 回归
- 建立 contributing.md / code review 流程

**阶段 3（6+ 月）：私有 Registry**
- 集团内自建 Skill Registry（可基于 mcp.so / Smithery 开源代码）
- 提供检索、评分、一键安装
- 接入集团 SSO + 审计

---

### 8.6 风险与坑点提示

**技术坑**：
1. **Skills 与 MCP 边界混淆**：Skills 是「能力包」，MCP 是「工具协议」，新人容易把工具逻辑写进 Skill。要明确：Skill 用 MCP，不重复造工具。
2. **知识库膨胀**：Markdown 写得太长，模型读不完。坚持「渐进式披露」——SKILL.md 主体精炼，详情按需 load。
3. **评估集污染**：用真实项目数据做评估集，可能泄露商业信息。脱敏 + 私有仓库。
4. **过度工程化**：第一版别上 LangGraph + Letta + 知识图谱全家桶，先用最简方案跑通再说。

**组织坑**：
5. **专家审批瓶颈**：所有更新都靠你一个人审，会变成瓶颈。需要培养 2-3 位「设计 Skill 维护者」。
6. **使用率低**：发布后没人用。要配合分享会、培训、案例展示。
7. **集团合规**：开源前过法务、安全、知识产权 review。
8. **Prompt 抄袭**：开源后 Prompt 内容可能被竞争对手抄走。建议核心方法论开源，专家级评估宪法保留私有版本。

**进化坑**（特别重要）：
9. **自动优化跑偏**：DSPy 优化出来的 Prompt 可能在评估集上得分高，但实际场景下变差。**必须保留专家最终决定权**。
10. **评估集变成 Goodhart's Law 受害者**：Agent 学会「应付评估集」而不是「真正做好评估」。定期更新评估集，加入对抗样本。
